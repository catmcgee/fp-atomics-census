# Batch-shape experiments

The revised harness targets vLLM 0.28.0. Its CPU analysis and integrity checks are tested locally, and the GPU controls and hook were run unchanged on one H100 stack on 14 September 2026; those arms carry `_v2_` in their names and sit beside the legacy arms under `probes/shape/results/e4/`. Do not reuse legacy arm directories or names.

Install the hook in the chosen GPU environment:

```sh
pip install -e probes/shape/shape_hook_pkg
```

Each arm directory is created once. Reusing it fails. Choose a new campaign root for each invocation, supply an immutable model `--revision`, and retain `run.json`, `env.json`, raw hook logs and raw outputs. The manifest includes the input prompts and their digest. Some binary/model content hashes remain explicitly unknown; collect them before making an exact-provenance claim.

## Compilation and graph controls

The controls are independent requests. For vLLM 0.28.0, the harness supplies explicit `CompilationMode` and `CUDAGraphMode` values:

| Arguments | Compilation | Graph mode |
|---|---|---|
| `--cudagraph 1` | VLLM_COMPILE | FULL_AND_PIECEWISE |
| `--cudagraph 0` | VLLM_COMPILE | NONE |
| `--no-compile --cudagraph 1` | NONE | FULL |
| `--no-compile --cudagraph 0` | NONE | NONE |

Full graph capture without compilation is model/backend dependent. Configuration resolution is recorded and checked at the driver and worker. A rejected or downgraded configuration is a failed arm, not a replacement for the requested arm. Recorded dispatch must also be reviewed to determine which modes actually ran; an enabled graph setting does not mean every pass uses a graph. Python hooks can be bypassed by compilation or graph replay, so absent mechanism observations are not zeros.

Legacy `graphs0` arms used `enforce_eager=True`, which disabled both features. Legacy `eager_graphs1` arms also resolved to no graphs. They cannot supply a four-arm factorial. New names include `v2` and distinguish compilation explicitly.

The four-arm factorial was run on 14 September 2026 on one H100 stack; the arms, their resolved modes and the audit's findings are in [campaigns/2026-09-14-h100.md](campaigns/2026-09-14-h100.md). The compiled MoE arms of that run executed a mis-compiled model: a hook-free check described there showed that torch.compile alone, not CUDA graphs, the hook or the compile cache, turns Qwen1.5-MoE-A2.7B-Chat's output degenerate on vLLM 0.28.0 on that stack, so their verdicts describe a degenerate configuration. vLLM 0.28.0 also reloads compiled graphs from `~/.cache/vllm/torch_compile_cache`, keyed by its configuration only; a forced quantisation choice made outside that configuration does not change the key, and the legacy compiled per-tensor FP8 arm executed the per-token graph. Run arms with `VLLM_DISABLE_COMPILE_CACHE=1` or clear the cache between arms, and keep the engine log, which prints `Directly load AOT compilation` on a hit. That variable disables vLLM's own compiled-artefact cache only. In the E6 matrix campaign each compiled replay, run on the same pod straight after its record, compiled its graph in 0.45 s and 0.29 s against 17.87 s and 5.56 s for the records, and the FP8 replay's DeepGEMM warm-up ran about 260 times faster, consistent with Inductor and kernel caches that the record process left on disk. When a replay must also recompile, clear those caches or start from a new container. That was done on 15 September for all eleven E6 records, on a different machine, and it changed five verdicts (see [campaigns/2026-09-15-h100-e6-cold.md](campaigns/2026-09-15-h100-e6-cold.md)). Clearing the caches means deleting the vLLM, Inductor, triton, NVIDIA, DeepGEMM, TileLang and CUTLASS caches and the temporary directories, listing every location and refusing to launch unless the total is zero files, then listing every file written afterwards. `VLLM_DISABLE_COMPILE_CACHE=1` is not a substitute: it covers vLLM's own artefact cache only, and it changes vLLM's compile-cache key, so a replay that sets it against a record that did not is running a different resolved configuration. Where that applied, the campaign reran the arm with the record's own environment as a control. The 15 September campaign shows the same pattern in all five compiled arms (replay compiles 0.30 to 0.83 s against 3.52 to 12.01 s for the records; the FP8 checkpoint's DeepGEMM warm-up 3.13 against 8,113.51 kernels per second) and one more consequence: a process whose traced graph is unchanged compiles as fast as a replay even with `VLLM_DISABLE_COMPILE_CACHE=1` (the failed per-tensor E6 attempt took 0.82 s straight after the per-token arm, consistent with reuse of that arm's Inductor artefacts), while a changed quantisation graph compiles at full cost (8.82 s for the corrected per-tensor record). A fresh compile time is a cross-check that a forced scheme changed the graph; it does not record the scheme.

## E2: conditional repeatability with the stock scheduler

```sh
python probes/shape/run_e2.py --model Qwen/Qwen2.5-7B-Instruct --revision MODEL_COMMIT --cudagraph 1 --prefix-caching 1 --repeats 12 --out results_new/e2
```

Vary compilation, graph and prefix settings in separate arms. New prompts include longer inputs; the legacy default accidentally contained only the four short prompts repeated four times. Each generated token must join to a non-null target observation; incomplete or duplicate joins invalidate the arm. Summaries distinguish repeated from singleton history groups.

## E3: scripted trajectory repeatability

```sh
RUN_TAG=a python probes/shape/run_e3.py --model Qwen/Qwen2.5-7B-Instruct --revision MODEL_COMMIT --out results_new/e3
RUN_TAG=b python probes/shape/run_e3.py --model Qwen/Qwen2.5-7B-Instruct --revision MODEL_COMMIT --out results_new/e3
python probes/shape/run_e3.py --compare results_new/e3/Qwen_Qwen2.5-7B-Instruct_tp1_none_compile_v2_graphs1_prefix1
```

The script adds eight requests, executes five scheduler steps, then adds eight more. `--mixed` uses long second-wave prompts and chunked prefill. Selected observations use offsets from the first actual forward pass. Complete trace lengths, normalised request sets, shapes and observations must agree for an identical verdict.

Until the 15 September correction `run_e3.py` accepted `--fp8-per-tensor` and added `_pertensor` to the arm name but never set `SHAPE_FORCE_FP8_PER_TENSOR`, so an E3 arm so labelled from an earlier tree ran vLLM's per-token default. No such arm is in the repository. The driver now sets the variable before `shape_hook.register()`, as E6 does (see Record below).

This does **not** test P2; E6 below does. A reconstruction experiment must record exact arrival/admission decisions, per-step token IDs and plans, rebuild prompt/KV state to the chosen boundary in a fresh process, teacher-force the recorded continuation and compare full observations. Neither repeated arrival scripts nor free-running output equality substitutes for those controls.

## E4: neighbour replacement

```sh
python probes/shape/run_e4.py --model Qwen/Qwen2.5-7B-Instruct --revision MODEL_COMMIT --target 0 --repeats 12 --out results_new/e4
python probes/shape/run_e4.py --model Qwen/Qwen1.5-MoE-A2.7B-Chat --revision MODEL_COMMIT --no-compile --cudagraph 0 --repeats 6 --out results_new/e4
python probes/shape/run_e4.py --model Qwen/Qwen2.5-7B-Instruct --revision MODEL_COMMIT --quantization fp8 --fp8-per-tensor --no-compile --cudagraph 0 --repeats 6 --out results_new/e4
```

Original and random-neighbour batches alternate. Prefix caching is disabled. Target slot is recorded and recovered in offline analysis. Use separate campaign roots for different target slots and lengths; a broader campaign should cover multiple positions, distinct targets, mixed prefill, shared prefixes and cache reuse. The current E4 driver does not implement those latter scheduling/cache scenarios. Its null results apply only to the configuration actually run.

No common-prefix truncation is allowed. Summaries are derived files; raw `runs.json` and hook logs are never rewritten during analysis. Per-expert counts inferred from router logits are labelled estimates separately from counts obtained from actual selected expert IDs. Changed counts/scales are mechanism diagnostics, not causal isolation.

## E5: recorded-stack comparison

```sh
python probes/shape/run_e5.py results_h100/e3/ARM/a results_other/e3/ARM/a
```

This compares aligned complete traces and reports a two-stack result. It does not isolate GPU architecture when drivers/configurations differ, or after free-running token divergence. Use identical teacher-forced tokens, weights, tokenizer and controlled software versions for a separate GPU comparison. The E6 cross-SKU replay does this for tokens, weights, tokenizer and Python packages; the attention kernel version, driver and compiled artefacts still differed.

## E6: reconstruction of a recorded execution (P2)

```sh
python probes/shape/run_e6.py --record --model Qwen/Qwen2.5-7B-Instruct --revision MODEL_COMMIT --out results_new/e6
python probes/shape/run_e6.py --record --model Qwen/Qwen2.5-7B-Instruct --revision MODEL_COMMIT --mixed --out results_new/e6
python probes/shape/run_e6.py --replay results_new/e6/ARM/record --out results_new/e6/ARM/replay
python probes/shape/run_e6.py --replay results_new/e6/ARM/record --out results_new/e6/ARM/boundary_12 --boundary 12
python probes/shape/run_e6.py --compare results_new/e6/ARM/record results_new/e6/ARM/replay
```

E6 was first run on one H100 stack (driver 580.126.09, torch 2.13.0+cu130, vLLM 0.28.0, FlashAttention 3, `CompilationMode` 3 with `FULL_AND_PIECEWISE` graphs, V1 model runner), Qwen2.5-7B-Instruct at revision a09a35458c702b33eeacc393d103063234e8bc28, a plain arm (37 passes, 512 rows) and a `--mixed` arm (77 passes, 555 rows, 43 partial prefill-chunk rows). Both replays were IDENTICAL with every requirement met; the boundary rebuild of plain pass 12 was DIFFERS in `h` and `logits_h` for all 16 rows with the argmax equal in all 16; the boundary gate refused every pass of the mixed record (a prefill chunk row in passes 0-3 and 5-45, prefixes above the 128-token budget in the all-decode passes). The GPU run used the code at commit 5a3815a; the comparison in this tree reproduces the same verdicts and counts, changing only the analyser digest (see [campaigns/2026-09-14-h100.md](campaigns/2026-09-14-h100.md)). It is the experiment E3 does not perform: the second run is driven from the first run's record, not from the arrival script, and the recorded tokens are teacher-forced. A second campaign on another pod with the same recorded stack ran the plain script once per model on Qwen3-8B-FP8 at 220b46e3b2180893580a4454f21f22d3ebb187d3 (the checkpoint's blockwise FP8, `CompilationMode` 3, `FULL_AND_PIECEWISE`), Llama 3.1 8B Instruct from NousResearch/Meta-Llama-3.1-8B-Instruct at d10aef7999a2b5ba950ab3974312feeedbfe0b77 (the gated meta-llama repository was not accessible; the mirror's weight shards share its digests; `CompilationMode` 3, `FULL_AND_PIECEWISE`) and Qwen1.5-MoE-A2.7B-Chat at ec052fda178e241c7c443468d2fa1db6618996be (`--no-compile --cudagraph 0`): 37 passes and 512 rows each, every replay IDENTICAL with every requirement met, with the code of census commit 50aae53 and `VLLM_DISABLE_COMPILE_CACHE=1` (see [campaigns/2026-09-14-h100-e6-matrix.md](campaigns/2026-09-14-h100-e6-matrix.md)). An `fp8` token in an E6 arm name records `--quantization`; for a checkpoint that is already FP8 it selects the checkpoint's own scheme, which for Qwen3-8B-FP8 is blockwise, not per-token.

**15 September arms.** A two-GPU H100 pod with the same recorded versions of torch, vLLM, FlashInfer and triton (openai differs) ran six arms with the code at 50aae53, each replayed once and IDENTICAL with every requirement met ([campaigns/2026-09-15-h100-e6-matrix2.md](campaigns/2026-09-15-h100-e6-matrix2.md)): Qwen2.5-7B-Instruct at `--tp 2`, plain (37 passes, 512 rows) and `--mixed` (77 passes, 555 rows); Qwen1.5-MoE-A2.7B-Chat `--no-compile --cudagraph 1` (FULL graphs on every pass); Qwen3-8B-FP8 `--mixed`; Qwen2.5-7B-Instruct `--quantization fp8` (per-token dynamic activation scales) and `--quantization fp8 --fp8-per-tensor`, the latter recorded and replayed with the driver correction described under Record, its per-tensor operation inferred rather than recorded. At TP above 1 the hook writes `rank<r>.jsonl` and `forcing_rank<r>.jsonl` per rank and the comparison reads rank 0; the other ranks' files enter only the digests. The hashed hidden state is the input to `compute_logits`, taken after the all-reduce, so no per-rank partial result is compared. In these records and their warm replays the ranks' hashes are equal; that is an observation, not a guarantee, and one cold TP=2 replay has 4 of 555 rows where they are not. If NCCL fails at `ncclCommInitRank` with an NVLS bind error, `NCCL_NVLS_ENABLE=0` is an environment change: apply it to record and replay alike and state it in the campaign note. The 15 September TP=2 arms needed it, and their `env.json` files, written by the code at 50aae53, record only `NCCL_ALGO`, `NCCL_PROTO`, `NCCL_MAX_NCHANNELS` and `NCCL_P2P_DISABLE`; `env.json` now also records `NCCL_NVLS_ENABLE` among the flags and every `NCCL_*` variable set in the process under `nccl_env`. Those replays ran in new processes on the same pod with warm caches, TP=2 on one NVLink pair with NVLS off; SGLang E6, TP above 2 and these arms on other GPU models have not been run. The cold-cache replay is described next; the one cross-SKU replay, below, is of the 14 September plain record.

**15 September cold replays.** All eleven records were replayed once more on a different two-GPU H100 pod running the same vLLM 0.28.0 stack, with every compile and kernel cache cleared and verified empty beforehand, the same driver and the same packages bar openai in the five 14 September records ([campaigns/2026-09-15-h100-e6-cold.md](campaigns/2026-09-15-h100-e6-cold.md)). The four compiled FP8 arms and the two uncompiled MoE arms are IDENTICAL; the five compiled bf16 arms are DIFFERS from pass 0, slot 0, in 493 to 555 of their rows, with every requirement met and every token held by teacher forcing. Three consequences for the procedure. A warm same-pod replay does not predict a cold one for a compiled bf16 arm, so a campaign that reports only warm replays should say so in those words. Two cold replays of one record on one machine differed in 5 of 512 rows, so a single IDENTICAL verdict is not a stable property and a repeat is worth its cost. At TP above 1 the comparison reads rank 0 only, and one cold TP=2 replay had 4 of 555 decode rows where the ranks' hidden-state hashes differ while the full-logit hashes and the argmax agree, so a TP=2 verdict should be read as a rank 0 verdict.

**Cross-SKU replay.** The plain record was replayed once on an RTX PRO 6000 Blackwell Server Edition into `results/e6/ARM/replay_sm120` with the same installed distributions, the code at 50aae53 and a fresh compile; every requirement held and the verdict was DIFFERS in all 512 rows, with 2 rows, one tied prompt position seen twice, whose free-running argmax differed from the forced token ([campaign note](campaigns/2026-09-14-sm120-crosssku.md)). The requirements compare the attention backend by name only. vLLM ran FlashAttention 3 for the record and FlashAttention 2 for the replay, and its selection does not allow version 3 above compute capability 9, so a Hopper `FLASH_ATTN` record cannot have its attention kernel replayed on Blackwell. vLLM 0.28.0 does not read `VLLM_ATTENTION_BACKEND` (it logs the variable as unknown). For any cross-SKU replay, keep the engine logs of both sides and report the FlashAttention version, the driver, the container image and whether each side compiled fresh or loaded a cached graph (`Directly load AOT compilation`); a same-stack replay that loads the record's compiled graph is not a fresh-compile control.

**Record.** `--record` runs the E3 arrival script (eight requests, five scheduler steps, eight more, run to completion) on the in-process engine core with prefix caching off, greedy sampling, `ignore_eos`, a fixed `max_tokens`, async scheduling off and the V1 model runner (the driver sets `VLLM_USE_V2_MODEL_RUNNER=0` unless the variable is already exported, and refuses to run if the resolved configuration is the V2 runner or async scheduling; vLLM 0.28.0 has two GPU runners and only the V1 runner accepts custom logits processors, so both arms run it and record which one ran). `--mixed` adds long second-wave prompts with `max_num_batched_tokens=128` and chunked prefill. `--fp8-per-tensor` sets `SHAPE_FORCE_FP8_PER_TENSOR` before the driver calls `shape_hook.register()`, which reads the variable once; with the in-process engine core at TP=1 the plugin load at engine start does not read it again. Before the 15 September correction the driver set it afterwards, so a TP=1 per-tensor arm silently ran vLLM's per-token default; `tests/test_fp8_forcing_order.py` checks the order for E2, E3, E4 and E6. Under compilation the hook records no FP8 scale, and neither `env.json` nor the hook records the forcing, so a compiled per-tensor arm is attested only indirectly (the 15 September campaign note lists the checks used). The arm directory `results_new/e6/ARM/record` is created once and holds `run.json` (with the resolved scheduler limits and model runner), `env.json`, raw hook logs, `outputs.json` and a derived `schedule.json`.

**Schema 3 records.** Every schema 2 field keeps its name and meaning. Each row adds `new_token_ids` (the ids the row consumed, positions `computed .. computed+q-1`, read from the runner's per-request host state) and `prompt_sha256` (SHA-256 over the request's prompt ids as u32 little-endian). Each record adds `admitted` (requests scheduled for the first time in that pass, with their full `prompt_token_ids`, `num_computed_tokens` and `prompt_sha256`), `resumed`, `finished`, `preempted` (from `scheduler_output.finished_req_ids` and `preempted_req_ids`, which the 0.28.0 scheduler fills for both runners), `model_runner` and `scheduler` (`max_num_seqs`, `max_num_batched_tokens`, `enable_chunked_prefill`, `async_scheduling`). Empty scheduler calls also carry `finished` and `preempted`. A row whose ids cannot be read, whose count is not `q`, that contains a placeholder id or that disagrees with the admitted prompt carries `invalid` with a reason, and the analysers treat it as an error. Schema 2 records cannot drive or validate a replay: they carry lengths and hashes but no token ids or admission events. `run_e6.py` rejects them with that reason in every mode; it never skips them.

**Replay.** `--replay` reads only the record. It first checks the record can be replayed (schema 3 everywhere, no invalid rows, every request admitted once with prompt ids and no cache hit, every consumed position covered without gaps, each pass's recorded argmax equal to the id consumed next, the derived continuation equal to `outputs.json` and `max_tokens` long) and refuses with the reasons otherwise. It then starts a fresh engine with the recorded settings and, before the step that produces each recorded pass index, adds exactly the requests the record admitted there as `TokensPrompt` with the recorded ids, the same request slot ids and the same sampling settings. Forward passes are counted at the in-process scheduler, so the alignment does not depend on hook state and works for any tensor-parallel size by construction (exercised at TP=1 and TP=2). The recorded continuation is teacher-forced: `teacher_forcing.TeacherForcingLogitsProcessor` receives each request's forced ids through `SamplingParams.extra_args`, and at every sampling step keeps the recorded next token's logit and sets every other logit of that row to the most negative finite value, so greedy sampling selects the recorded token even after a numerical divergence and the replayed inputs stay equal to the recorded ones. The processor runs after vLLM takes the raw top-k logprobs and after the hook takes its `argmax`, so those remain free-running observations; comparing the replayed `argmax` with the recorded one (the forced token) says, per pass and row, whether the free-running choice at that pass differs from the recorded one given the identical forced inputs; after the first such row an actual free run would have had different inputs. The processor also writes `forcing_rank<r>.jsonl` with the argmax it saw before masking; the comparison requires one call per forward pass and agreement with the hook. Its `rows_where_forced_equalled_argmax` count is a diagnostic, not the divergence signal. A partial prefill chunk row is sampled and the sample discarded (`gpu_model_runner.py` marks the row in `discard_request_mask` and clears its sampled token in `_bookkeeping_sync`), and for such a row the processor forces the request's first output token while the row's logits predict the next prompt token, so the two are expected to disagree and the count is uninformative wherever chunked prefill splits a prompt; in the recorded mixed arm 42 of the 43 partial rows disagreed and one agreed by coincidence. The processor forces nothing in a record arm, so the count is a replay-side quantity. The divergence signal is the hook's recorded-versus-replayed `argmax` comparison. Limits: one sampled token per request per pass (no speculative decoding), greedy sampling only, async scheduling off (the V1 runner otherwise holds a placeholder instead of the sampled id on the host), and a run that preempted requests relies on the stock scheduler preempting again; the comparison checks it.

**Compare.** `--compare` fails closed. Requirements, checked in order and each naming the first offending pass, slot and field: equal trace lengths; equal request slot order per pass; equal `num_reqs`, `total_scheduled`, `dispatch`, `attention_backend`, `parallel`, `resolved_compile`, `resolved_cudagraph`, `model_runner`, `scheduler`, `finished`, `resumed` and `preempted` per pass; equal `q`, `computed`, `prompt`, `kv` and `cache_hit` per row; equal `new_token_ids` per row. Any mismatch is NOT COMPARABLE. Only when all hold are `h`, `argmax` and `logits_h` compared per row and pass, giving IDENTICAL or DIFFERS with the first divergent pass and slot and row counts. Provenance failures (missing forcing log, replay not referencing the recorded run id, differing model runners, record files whose digests differ from those the replay's `run.json` recorded, a record whose status is not `configured`, truncated outputs) are INVALID. The summary is written next to the two arms with input and analyser digests, named per replay directory so repeated replays of one record keep separate derived files: `ARM/summary.json` for a directory named `replay`, `ARM/summary_NAME.json` for any other replay directory, `ARM/boundary_T.json` for a directory named `boundary_T`. A replay summary also records each side's GPU and driver from its `env.json` and says in `claim_scope` whether GPU, GPU count, driver and installed distributions are equal on both sides; equal fields do not make two stacks equal, because the attention kernel version, the container image and compiled artefacts are not recorded there. Raw files are never rewritten. `make reanalyse` recomputes every `results/e6/*/summary*.json` and `boundary_*.json`.

**Boundary mode.** `--boundary T` rebuilds recorded forward pass `T` only, with the stock scheduler, and is sound only under conditions the plan checks before starting: every row of `T` is a single-token decode row, the rows' recorded prefixes (positions `0 .. computed-1`) fit one prefill pass (`sum(computed) <= max_num_batched_tokens` and rows `<= max_num_seqs` from the recorded run), and the record covers every needed position. The rebuilt run adds one request per row in recorded order with the prefix as its prompt and the two recorded next tokens forced; the scheduler then prefills all rows in its first pass and the second pass is a uniform decode with every row at its recorded `computed` and `kv`. `--compare` recognises the `boundary.json` plan, compares recorded pass `T` with that second pass (excluding `prompt` and `cache_hit`, which are the prefix length by construction) after checking that the rebuilt prefill rows consumed exactly the prefix the record derives for each row, and writes `boundary_T.json`. Passes containing prefill chunk rows cannot be rebuilt because the scheduler, not the caller, fixes chunk boundaries; the mode exits with that reason. The rebuilt KV state comes from one prefill pass rather than the recorded sequence of passes, so IDENTICAL supports P2 for that pass while DIFFERS does not separate a prefill-versus-decode KV difference from other causes.

## Offline regeneration

```sh
python probes/shape/run_e2.py --analyse SAVED_E2_ARM
python probes/shape/run_e4.py --analyse SAVED_E4_ARM
python probes/shape/run_e3.py --compare SAVED_E3_ARM
python probes/shape/run_e6.py --compare SAVED_E6_ARM/record SAVED_E6_ARM/replay
make shape-tables
make check-derived
```

Input and analyser SHA-256 digests identify each generated summary. Legacy empty scheduler calls are excluded; new hooks record them explicitly as non-forward events. Missing data is reported as invalid or untested, never as a null result. `make check-derived` performs reanalysis in a temporary copy to detect stale files without overwriting evidence.
