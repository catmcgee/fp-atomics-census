## Findings the audit established from the raw logs

- **The legacy compiled forced-per-tensor FP8 arm did not execute per-tensor quantisation.** The legacy arm `Qwen_Qwen2.5-7B-Instruct_tp1_fp8_pertensor_graphs1_prefix0` (compile and graphs, verdict IDENTICAL) holds, for every one of its 796 forward passes and all 16 requests (14,708 request rows), hidden-state hashes identical to the legacy per-token arm `Qwen_Qwen2.5-7B-Instruct_tp1_fp8_graphs1_prefix0` recorded fourteen minutes earlier on the same pod, with identical shape vectors, target tokens and argmax; the only difference between the two logs is the `fp8_scale_first_call` key added by a later commit. The legacy forced-per-tensor eager arms differ from the per-token compiled arm at all 32 target steps and agree with each other at all 32. Two compiled runs whose hidden states agree bit for bit on batches whose activation maxima differ executed the same activation quantisation, so the legacy compiled "per-tensor" row is a second per-token measurement and is not evidence for or against X2 under compilation. The cause is not recorded. Candidate mechanism, consistent with the vLLM 0.28.0 source and with the new engine logs but not verifiable for the legacy pod: vLLM saves and reloads compiled graphs from `~/.cache/vllm/torch_compile_cache/torch_aot_compile/<hash>/`, keyed by `VllmConfig.compute_hash()` plus a checksum of the traced model files; neither the `SHAPE_FORCE_FP8_PER_TENSOR` variable nor a monkeypatched Python function enters that key, and the two legacy arms had identical configurations. The new compiled FP8 arms are not affected as far as the records show: their engine logs show a fresh compile with the forcing active, and no per-token FP8 arm ran on the new pod.
- **The compiled MoE arms describe a degenerate configuration.** In both new compiled MoE arms the original batch's target tokens are the two-token cycle `279, 198, 1782, 198, 1782, ...`; five of six dummy batches give the same cycle and one gives `279, 198, 5689, 5403, 198, 5689, 5403, ...`. The uncompiled arms give a non-repeating continuation, identical for the original and every dummy batch and identical token for token to the legacy eager MoE arm. The legacy compiled MoE arm and the legacy E2 compiled MoE arm are degenerate in the same way (repeated tokens or short cycles). Under compilation the first-layer routing of the identical original batch is almost uniform (60 to 63 tokens for 56 experts and 116 for four) and moves by an L1 distance of 448 to 464 of 7,696 when every neighbour is replaced; under eager execution the counts range from 0 to 240 and move by 3,440 to 3,590. The records establish that `custom_ops` was `['none']` under compilation and `['all']` without it, that no fusion pass was enabled and that the MoE backend was `TritonExperts` in both, but not which computation differs. Whether this is a vLLM or Inductor defect for Qwen2MoE, an interaction with the hook (which patches `FusedMoERouter.select_experts` before compilation) or something else is not determined. A compiled MoE run without the hook has not yet been done. The dense compiled arms produce coherent tokens with the same hook.

## det_strict

`probes/probe_torch_ops.py` through `probes/invoke.py`, `RUN_TAG=a` (run id `fbee4a5d-28d7-4d60-abf5-91b8613cf629`, 19:26Z) and `RUN_TAG=b` (run id `29bd8bd5-70f6-4acf-a1d6-2f20ebe0eb6f`), eight reports each under `probes/results/NVIDIA-H100-80GB-HBM3-580.126.09-torch2.13.0+cu130/<run id>/` plus `probes/results/invocations/<run id>/status.json` (`NONIDENTICAL_OR_REJECTED`, return code 1). Every `_det_strict` report records `deterministic_algorithms true` and `deterministic_warn_only false`. `index_add_det_strict`, `scatter_add_det_strict` and `cumsum_float_det_strict` are bitwise-identical in process (4 evaluations per report) and across the two processes (equal baseline hashes, shared comparison key). `bincount_weights_det_strict` is `REJECTED` in both processes with `_bincount_cuda does not have a deterministic implementation`; the analyser renders a rejection as INVALID / n/a / 0, never as a result. The `_default` arms differ for `index_add_`, `scatter_add_` and weighted `bincount` and are identical for float `cumsum`, as in the legacy H100 reports. `CUBLAS_WORKSPACE_CONFIG` was unset; none of the four operators uses cuBLAS.

Because the run directories sit inside the legacy stack directory, the report tooling now pairs fresh-process comparisons only within one campaign (reports sharing a probe source digest) and lists the legacy and the new campaign as separate rows; see `triage/attach_runtime.py`.

## Deviations, as corrected by the audit

1. `/workspace` on the pod is a network volume with about 45 ms per small-file operation. The virtual environment, pip cache and Hugging Face cache were placed on the container disk (`/root/venv`, `/root/pip-cache`, `/root/hf`); code and results stayed under `/workspace/census`.
2. Model prefetch used a separate small environment (`huggingface_hub` and `hf_transfer`) because the system Python is externally managed.
3. `ninja` was not installed by `vllm==0.28.0 flashinfer-python==0.6.16.post3`. The first attempt of the compiled FP8 graphs-1 arm failed during engine warm-up with `FileNotFoundError: 'ninja'`. The audit corrected the attribution: the traceback is FlashInfer's sampling JIT (`flashinfer/jit/core.py`, `run_ninja`) invoked from vLLM's sampler warm-up, not torch.compile or Inductor; torch.compile had completed and saved its AOT artifact before the failure. `pip install ninja` (1.13.2) fixed the missing package.
4. The second attempt failed the same way because the runner scripts called the venv interpreter directly and the venv `bin/` was not on `PATH`; `export PATH=/root/venv/bin:$PATH` fixed it.
5. The third attempt, which produced the recorded arm, loaded the AOT artifact saved by attempt 1 (`Directly load AOT compilation` in its engine log). Same command line and same forcing, so no contamination, but the harness records nothing about cache loads. The same mechanism is the candidate cause of the legacy FP8 finding above. For future campaigns run each arm with `VLLM_DISABLE_COMPILE_CACHE=1` or clear `VLLM_CACHE_ROOT` between arms, and keep the engine log.
6. The two failed attempt directories contained only an empty `hook/` directory (no `run.json`, no log); Git stores no empty directories, so they are not committed. Their record is this note and the engine logs below.
