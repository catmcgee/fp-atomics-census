## Findings the audit established from the raw logs

- **The legacy compiled forced-per-tensor FP8 arm did not execute per-tensor quantisation.** The legacy arm `Qwen_Qwen2.5-7B-Instruct_tp1_fp8_pertensor_graphs1_prefix0` (compile and graphs, verdict IDENTICAL) holds, for every one of its 796 forward passes and all 16 requests (14,708 request rows), hidden-state hashes identical to the legacy per-token arm `Qwen_Qwen2.5-7B-Instruct_tp1_fp8_graphs1_prefix0` recorded fourteen minutes earlier on the same pod, with identical shape vectors, target tokens and argmax; the only difference between the two logs is the `fp8_scale_first_call` key added by a later commit. The legacy forced-per-tensor eager arms differ from the per-token compiled arm at all 32 target steps and agree with each other at all 32. Two compiled runs whose hidden states agree bit for bit on batches whose activation maxima differ executed the same activation quantisation, so the legacy compiled "per-tensor" row is a second per-token measurement and is not evidence for or against X2 under compilation. The cause is not recorded. Candidate mechanism, consistent with the vLLM 0.28.0 source and with the new engine logs but not verifiable for the legacy pod: vLLM saves and reloads compiled graphs from `~/.cache/vllm/torch_compile_cache/torch_aot_compile/<hash>/`, keyed by `VllmConfig.compute_hash()` plus a checksum of the traced model files; neither the `SHAPE_FORCE_FP8_PER_TENSOR` variable nor a monkeypatched Python function enters that key, and the two legacy arms had identical configurations. The new compiled FP8 arms are not affected as far as the records show: their engine logs show a fresh compile with the forcing active, and no per-token FP8 arm ran on the new pod.
- **The compiled MoE arms describe a degenerate configuration.** In both new compiled MoE arms the original batch's target tokens are the two-token cycle `279, 198, 1782, 198, 1782, ...`; five of six dummy batches give the same cycle and one gives `279, 198, 5689, 5403, 198, 5689, 5403, ...`. The uncompiled arms give a non-repeating continuation, identical for the original and every dummy batch and identical token for token to the legacy eager MoE arm. The legacy compiled MoE arm and the legacy E2 compiled MoE arm are degenerate in the same way (repeated tokens or short cycles). Under compilation the first-layer routing of the identical original batch is almost uniform (60 to 63 tokens for 56 experts and 116 for four) and moves by an L1 distance of 448 to 464 of 7,696 when every neighbour is replaced; under eager execution the counts range from 0 to 240 and move by 3,440 to 3,590. The records establish that `custom_ops` was `['none']` under compilation and `['all']` without it, that no fusion pass was enabled and that the MoE backend was `TritonExperts` in both, but not which computation differs. From these records alone the audit could not tell whether this is a vLLM or Inductor defect for Qwen2MoE, an interaction with the hook (which patches `FusedMoERouter.select_experts` before compilation) or something else. The hook-free check below, run afterwards on the same pod, excludes the hook, CUDA graphs and the compile cache: torch.compile alone switches this model's output between the two behaviours. The dense compiled arms produce coherent tokens with the same hook.

## Hook-free compiled MoE check

Run afterwards on the same pod (21:02Z to 21:07Z) to answer whether the degenerate compiled MoE output needs the shape hook, and whether torch.compile or CUDA-graph capture is the switch. One model (Qwen/Qwen1.5-MoE-A2.7B-Chat at `ec052fda178e241c7c443468d2fa1db6618996be`), one stack, the 16 `mixed_prompts()` prompts passed as token ids (verified equal to the E4 `run.json` prompt list), greedy, 32 tokens, `ignore_eos`, TP=1, `max_model_len 2048`, prefix caching off, `enforce_eager=False`, `compilation_config={"mode": 3 or 0, "cudagraph_mode": ...}`, the same engine construction as `shape_common.engine_kwargs` without the hook. Toggling CUDA graphs changed no token in either compile setting (16 of 16 prompts identical between the two compile arms and between the two no-compile arms); switching compilation mode 3 to 0 changed every prompt (0 of 16 identical). The cache-enabled control compiled fresh under a new key (its log has `saved AOT compiled function` and no `Directly load AOT compilation`) and is token-identical to the cache-disabled compile arm; the `custom_ops=['all']` control is degenerate in 9 of 16 prompts and agrees with the default compile arm on 8 of 16, including prompt 0. Plugin-disable proof: `SHAPE_HOOK_OUT`, `SHAPE_RUN_ID`, `SHAPE_EXPECT_*` and `SHAPE_FORCE_FP8_PER_TENSOR` unset; `VLLM_PLUGINS=""`, which vLLM 0.28.0 parses as an allowlist matching no plugin, so the `shape_hook` general plugin (and the two LoRA resolver plugins) were skipped; `VLLM_ENABLE_V1_MULTIPROCESSING=0`, so the model ran in the checked process. Each log records, before engine construction and after `LLM(...)` returned, `shape_hook_in_sys_modules: false`, `vllm_plugins_loaded_flag: true` after construction, `envs.VLLM_PLUGINS: [""]` and `FusedMoERouter.select_experts` still resolving to `vllm.model_executor.layers.fused_moe.router.fused_moe_router` (the hook replaces that method at class level when active). `VLLM_DISABLE_COMPILE_CACHE=1` for the four main arms and the `custom_ops` control; every compile log shows a fresh compile and none contains `Directly load AOT compilation`.

Consequence for the E4 rows: the compiled MoE arms ran a mis-compiled model. torch.compile, not CUDA graphs, not the hook and not the compile cache, changes this model's output on this stack. Their DIFFERS verdicts are observations on a degenerate configuration and are not evidence for prediction P4; the rows stay in the tables. The uncompiled MoE arms, whose output is not degenerate, were IDENTICAL under neighbour replacement although the per-expert counts changed, so on this stack the MoE content coupling predicted by X1 was not observed in a valid configuration. One model, one stack. Reported to vLLM as [vllm-project/vllm#56900](https://github.com/vllm-project/vllm/issues/56900), opened 14 September 2026.

## Deviations, as corrected by the audit

1. `/workspace` on the pod is a network volume with about 45 ms per small-file operation. The virtual environment, pip cache and Hugging Face cache were placed on the container disk (`/root/venv`, `/root/pip-cache`, `/root/hf`); code and results stayed under `/workspace/census`.
2. Model prefetch used a separate small environment (`huggingface_hub` and `hf_transfer`) because the system Python is externally managed.
3. `ninja` was not installed by `vllm==0.28.0 flashinfer-python==0.6.16.post3`. The first attempt of the compiled FP8 graphs-1 arm failed during engine warm-up with `FileNotFoundError: 'ninja'`. The audit corrected the attribution: the traceback is FlashInfer's sampling JIT (`flashinfer/jit/core.py`, `run_ninja`) invoked from vLLM's sampler warm-up, not torch.compile or Inductor; torch.compile had completed and saved its AOT artefact before the failure. `pip install ninja` (1.13.2) fixed the missing package.
4. The second attempt failed the same way because the runner scripts called the venv interpreter directly and the venv `bin/` was not on `PATH`; `export PATH=/root/venv/bin:$PATH` fixed it.
5. The third attempt, which produced the recorded arm, loaded the AOT artefact saved by attempt 1 (`Directly load AOT compilation` in its engine log). Same command line and same forcing, so no contamination, but the harness records nothing about cache loads. The same mechanism is the candidate cause of the legacy FP8 finding above. For future campaigns run each arm with `VLLM_DISABLE_COMPILE_CACHE=1` or clear `VLLM_CACHE_ROOT` between arms, and keep the engine log.
6. The two failed attempt directories contained only an empty `hook/` directory (no `run.json`, no log); Git stores no empty directories, so they are not committed. Their record is this note and the engine logs below.
