**What `max_ulp` about 30,000 means.** The metric is the bf16 ordinal distance (`common.ulp_diagnostics`: +0.0 and -0.0 map to 0, the smallest positive to +1, the smallest negative to -1). Outputs are of order 0.1 to 1, so a same-sign pair cannot be 29,568 apart; every pair at that distance has opposite signs, and the distance is about 30,000 for magnitudes anywhere from about 1e-4 to 5e-2. `max_ulp` therefore shows that at least one element changed sign between evaluations in every comparison, including at top-k 1. It is not a relative error and must not be quoted as one. The open 3-or-more bucket mixes small differences with sign flips, so the recorded data cannot say how many of the 19.5% to 47.4% in that bucket are which; `ulp_diagnostics` now also records `sign_changes` and absolute-difference fields for future runs.

**Which kernels ran (inferred from the wheel source and the JIT log, not recorded by the probe).** `select_sm120_moe_backend` chooses the static kernel when `num_tokens * num_topk <= 640` and the dynamic kernel otherwise, so tokens16 (all top-k) and tokens512 topk1 ran the static kernel and the rest the dynamic (generic) kernel; the JIT log compiled `static_m16_k2048_n1024_t{1,2,4,8}_r{16,32,64,128}`, `static_m512_k2048_n1024_t1_r512` and `dynamic_e8_k2048_n1024_t{1,2,4,8}`. Both kernels compute FC2 one 128-wide intermediate slice at a time and scatter-add each slice's partial, rounded to bf16, into the output with `red.relaxed.gpu.global.add.noftz.bf16x2` (`moe_static_kernel.py:2164`, `_moe_dynamic/generic.py:2552` in 0.6.18.post1); the output is zeroed inside the kernel. Every output element therefore receives `(1024 / 128) * top_k` reduction adds: eight at top-k 1, sixty-four at top-k 8, from different CTAs in arrival order. The measurements are consistent with that design. They do not identify the stage that produces the differing bits, do not implicate the dense split-K GEMM (flashinfer-0011; the MoE kernels import that module for descriptor helpers and the probe never calls its opt-in split-K path), and say nothing about numerical correctness (`rel_max_err_vs_reference` 0.13 to 0.26 and `corr_vs_reference` 0.973 to 0.978 against an unquantised fp32 reference are a sanity diagnostic, not a validated bound). `extra.selected_backend` is null and `extra.cause_isolated` is false in every report. The pinned inventory sha `c0d920d3` has a different file layout from the wheel, so `operator_example` remains the evidence relation.

## Three-rank NCCL all-reduce (L40S)

Cancellation pattern: rank r fills a `1<<22` bf16 tensor with `(256.0, 1.0, -256.0)[r]`. In bf16, 256 + 1 rounds to 256 while 1 + (-256) = -255 is exact, so the rounded sum is 0.0 for the order ((256 + 1) + (-256)) and 1.0 for the two other orders; the result depends on the reduction order by construction. Random pattern: `torch.randn` with seed equal to the rank.

Every one of the 24 reports is bitwise-identical in process (four evaluations) and the a and b processes share both the comparison key and the baseline hash, so the fresh-process column is computed, not defaulted:

| Configuration | Pattern | `first_hash` (all ranks, both tags) | Reading |
|---|---|---|---|
| default | cancellation | `a7733b1f3dfd` | matches neither all 1.0 (`3d98e0f9f3c8`) nor all 0.0 (`2ac36c3b935b`) nor all -0.0 (`5c3147c563e1`), so the default configuration reduced different elements in different orders and produced a mixture of the two reachable roundings; the element layout is not recorded |
| Tree, Simple, 1 channel | cancellation | `3d98e0f9f3c8` | equals the hash of a `1<<22` bf16 tensor of 1.0 (rank 1's input hash): 1.0 in every element |
| default | random | `153e2bee9d45` | differs from the Tree result for identical inputs |
| Tree, Simple, 1 channel | random | `6fb7b90c4dfc` | differs from the default result for identical inputs |

Input hashes: cancellation ranks 0, 1, 2 `7638d7954850`, `3d98e0f9f3c8`, `25e8c9a37623`; random `469bd8675d60`, `291bdf9931df`, `bfd9bd83f5fd`. Eight evaluations per arm are two processes of one baseline plus three comparisons; the sample is small.

**Transport.** With default NCCL settings the three-rank all-reduce never returned: the probe workers sat at 100% CPU for more than 110 s without writing a report and were terminated (`hung_attempt_*.log`, SIGTERM, exit 143, no reports). A standalone diagnostic with `NCCL_DEBUG=INFO` (`nccl_diag.py`, `nccl_diag.log`) completed ring setup (NCCL 2.27.7+cuda13.0, `Channel 00/02 : 0 1 2`, `isAllDirectP2p 0`, 2 coll channels, 0 nvls channels, all three `Init COMPLETE`), connected 0 to 1 via P2P/CUMEM and 1 to 2 and 2 to 0 via SHM/direct, then hung in `all_reduce` until a 100 s timeout. `NCCL_CUMEM_ENABLE=0` also hung (`nccl_diag_cumem0.log`). `NCCL_P2P_DISABLE=1` completed in 0.3 s with the expected value 3.0 (`nccl_diag_p2p0.log`). Every recorded L40S report therefore ran with `NCCL_P2P_DISABLE=1`, that is over the shared-memory transport, and `env.env.NCCL_P2P_DISABLE` is `"1"` in all 24. Disabling P2P changes the transport and can change NCCL's algorithm and protocol choice, so "default" in these rows means the default algorithm under a forced SHM transport on this PCIe topology. The default-transport configuration was not measured. The legacy two-rank rows are from an H100 pair and are not comparable.
