The resolved vLLM configuration is equal apart from the model path strings and the compile cache directory derived from them. `VLLM_ATTENTION_BACKEND=FLASH_ATTN` was exported for the replay and appears in its `env.json` and hook records, but vLLM 0.28.0 logged it as an unknown environment variable, so the backend was vLLM's default choice on both GPUs. vLLM's selection prefers FlashAttention 3 only on compute capability 9 and does not allow it on 10 and above (as read in the pinned vLLM source), so the record's attention kernel cannot run on this GPU.

Result (`summary_replay_sm120.json`; the audit reproduced the pod's file byte for byte offline with the analyser at 50aae53): every requirement met, including equal dispatch in all 37 passes (2 PIECEWISE passes padded to 496 tokens, 26 FULL padded to 16, 9 FULL padded to 8), the attention backend name, the scheduler limits and every row's consumed token ids. `h` and `logits_h` differ in 512 of 512 rows, in all 37 passes, from pass 0 slot 0; verdict **DIFFERS**. The forcing log has 37 calls and 512 forced rows, and the free-running `argmax` equals the forced token in 510 of 512 rows. The two exceptions are pass 4 slot 0 and pass 9 slot 8, forced 1779 and free 2548 in both: `mixed_prompts()` repeats eight prompts, so slots 0 and 8 carry the same prompt, and at that position the H100 record's logprobs for tokens 1779 and 2548 are bit-identical (about -2.389), an exact tie resolved to the lower id; on SM120 token 2548 is 0.125 ahead. The record holds 12 positions where the forced token ties exactly with another listed token; nine stay tied on SM120, one resolves towards the forced token and these two against it. Outputs: all 16 forced token sequences equal, no output hash equal; a top-5 logprob value changed at 509 of 512 positions and the listed token set at 63; the forced token's logprob moved by at most 0.113 (median 0.00014); the largest shift of any listed token, 1.31, is a tail entry whose logprob moved from -14.69 to -13.38, and among entries above -5 the largest shift is 0.246.

What this shows and does not show. On this pair of stacks, with the recorded shapes, dispatch, backend name, scheduler limits and token ids all equal, the SM120 replay reproduced none of the H100 record's hidden-state or logit hashes, while the free-running choice changed only where the record held an exact tie. It is a two-stack observation, not an isolated GPU effect: the FlashAttention major version, the driver, the container image and every compiled artefact differ, and the same-stack H100 replay that was IDENTICAL loaded the record's compiled graph (`Directly load AOT compilation`), whereas this replay compiled fresh. The hook records the attention backend by name only, which is why the requirements could hold across a change of attention kernel. No kernel is identified. The pod's summary carried the analyser's fixed same-stack `claim_scope`, which did not describe this replay; the analyser now compares the GPU, GPU count, driver and installed distributions in the two `env.json` files, records each side's GPU and driver, and the committed summary states a two-stack scope. Regenerating it changed only that text, those fields, the analyser digest and the two added `env.json` input digests. One replay, one record, one pair of stacks.

## FlashInfer main: SM120 b12x fused MoE

A second virtual environment took torch 2.14.0+cu130 (CUDA 13.0, cuDNN 92400) and FlashInfer built from its main branch with `pip install --no-build-isolation "git+https://github.com/flashinfer-ai/flashinfer.git@main"`, which resolved to commit `5ed46a9ee125f167fd1070be9aa081d70e92b366` (version string 0.7.0, a development build; also nvidia-cutlass-dsl 4.7.1, triton 3.8.0, nvidia-nccl-cu13 2.30.7, numpy 2.5.3, ninja 1.13.2; 64 installed distributions per report). The build contains FlashInfer PR #4718 (merged 31 August 2026), after which the installed `moe_static_kernel.py` is byte-identical to the file at the merge commit: it stores one bf16 contribution per route and sums the routes in a separate fp32 finalise in fixed order, with no floating-point reduction instruction, and it still uses integer atomics for row allocation and work claiming. The dynamic kernel files (`_moe_dynamic/generic.py`, `moe_dynamic_kernel.py`, `moe_w4a16_fp4_helpers.py`) are byte-identical to the v0.6.18.post1 tag and still scatter with `red.global.add.noftz.v4.bf16x2`. The installed `select_sm120_moe_backend` picks the static kernel when tokens times top-k is at most 1024 for `quant_mode="nvfp4"` (640 for other modes, and 640 for every mode in 0.6.18.post1) and the dynamic kernel above; no override variable was set; the micro kernels need at most 8 tokens and were not reached. The JIT log compiled static kernels for exactly the six arms at or below 1024 routed pairs and dynamic kernels for the rest.

`RUN_TAG=a` and `RUN_TAG=b` `python invoke.py probe_flashinfer.py --which b12x_moe`, run ids `1c21ea59-d6ca-43d2-ae4f-63f16b82345b` (22:19:25Z) and `294a97d9-d6ca-4dee-950f-2c5ac7ecdd4d` (22:20:44Z), both `NONIDENTICAL_OR_REJECTED` with return code 1 and 12 measurements. Comparison keys, input tensor hashes and `extra` are equal between the tags in every arm; no warnings, no non-finite values; `selected_backend` null and `cause_isolated` false throughout.

Against the earlier SM120 runs of the same probe (all with flashinfer 0.6.18.post1 and a 640 cutover): the configurations that release sent to its static kernel differed in all three runs, and here all six static-dispatched configurations are identical; 512 tokens at top-k 2 moved from the dynamic kernel, where it differed in and across processes in the rerun, to the static kernel, where it is identical; the dynamic configurations differ as before, with mismatched shares and sign-change counts in the rerun's ranges (for example 4096 tokens at top-k 8: 75.1% to 75.8% of elements and 11,002 to 11,274 sign changes, against 74.9% to 75.7% and 11,001 to 11,140).

What this shows and does not show. For these six NVFP4 shapes (8 experts, hidden 2048, intermediate 1024), the static path of FlashInfer main at 5ed46a9 returned the same bits on repeated calls and in a second process, as PR #4718's description reports for its own shapes; the dynamic path of the same build did not, so repeatability holds within the static band only (at most 1024 routed pairs for NVFP4 at that commit). Two things changed since the 0.6.18.post1 rerun, the FlashInfer source and the cutlass-dsl version (4.8.0.dev0 to 4.7.1); the source reading explains the static change and the unchanged dynamic source still differs, but the measurement does not isolate the #4718 change. The executed kernel was inferred from the dispatch source and the JIT log, not recorded. The micro kernels, MXFP4 and other shapes were not measured. Eight evaluations per configuration on one host.
