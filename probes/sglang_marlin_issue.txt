[Bug] Marlin atomicAdd K-slice reduction is always on for n < 2048, k >= 2048 (dead `if not True:` guard) and is not disabled by --enable-deterministic-inference

## Describe the bug

`should_use_atomic_add_reduce` in `python/sglang/srt/layers/quantization/marlin_utils.py` (main `5c2de3f35567ffceec6cea86ba18e075692e9101`, lines 441 to 463) contains

```python
    # disable atomicAdd reduce by default,
    # one can enable it with VLLM_MARLIN_USE_ATOMIC_ADD=1
    # TODO: Need to add sglang's MARLIN_USE_ATOMIC_ADD: bool = False
    if not True:
        maybe_warn_marlin_atomic_add_env()
        return False
```

so the intended "off by default" branch is dead and the function returns True for every projection with `n < 2048` and `k >= 2048` on CUDA (except bf16 on pre-SM90 parts). `maybe_warn_marlin_atomic_add_env` (lines 425 to 438) has the matching `if True: return` stub and still refers to `VLLM_MARLIN_USE_ATOMIC_ADD`. The result is passed as `use_atomic_add` to the kernel from `apply_gptq_marlin_linear` (line 484), `apply_awq_marlin_linear` (line 554), `marlin_utils_fp8.py` (line 74) and `marlin_utils_fp4.py` (line 103).

With `use_atomic_add` set, the Marlin write-out (`marlin_template.h`, `atomicAdd(&C_half2[a], sh_red_half2[a])` under `if (use_atomic_add && slice_count > 1)`) adds each K-slice's partial sum into C with half2 or bf162 atomics. The summation order follows CTA scheduling, so the output is not bitwise reproducible between runs. vLLM gates the same kernel behind `VLLM_MARLIN_USE_ATOMIC_ADD`, default off.

The condition is evaluated on the fused, tensor-parallel-sharded weight (`n = output_size_per_partition`, `k = input_size_per_partition`). No projection of Qwen2.5-7B meets it at TP=1 or TP=2. The down projection of Qwen2.5-1.5B meets it at every tensor-parallel size the model admits (TP=1, 2 and 4: n=1536 with k=8960, 4480 and 2240), and so do narrow column-parallel shards such as Qwen2.5-7B `qkv_proj` at TP=4 (n=1152, k=3584).

`--enable-deterministic-inference` does not change this. The flag is mirrored into `SGLANG_ENABLE_DETERMINISTIC_INFERENCE` by `arg_groups/serving_hook.py`, but nothing on the Marlin path reads it.

PR #22616 by @ianliuy (opened 12 April 2026) already contained the fix for this guard (`SGLANG_MARLIN_USE_ATOMIC_ADD`, default off) together with 8-bit GPTQ test coverage. It received no maintainer review (the only review activity is from the gemini-code-assist bot) and was closed by the idle-PR bot on 28 August 2026 because the author had six PRs open with none updated in seven days, over the soft cap of five for idle PRs. A fresh PR that re-lands the guard fix follows this issue.

## Reproduction

Stack: sglang 0.5.19 (commit `b41552334d46`; the guard is byte-for-byte unchanged on main), NVIDIA H100 80GB HBM3 (SM90), driver 580.126.09, torch 2.13.0+cu130, CUDA 13.0, flashinfer-python 0.6.18, triton 3.7.1, Python 3.12.3.

Method: `sgl.Engine(model_path=..., tp_size=..., random_seed=0, disable_radix_cache=True)`, greedy decoding (`temperature=0`, `max_new_tokens=32`) over a fixed batch of 16 prompts (4 distinct prompts, each repeated 4 times), `return_logprob=True, top_logprobs_num=5`. The 512 sampled token IDs and the 2560 top-5 logprob values are compared bit for bit against a baseline over six repeats, in each of two fresh processes (14 evaluations and 12 comparisons per configuration). Top-5 values are compared as a flat vector without vocabulary labels; token IDs are retained. Script: `probes/probe_engine_logits.py` in https://github.com/catmcgee/fp-atomics-census; reports under `probes/results/NVIDIA-H100-80GB-HBM3-580.126.09-torch2.13.0+cu130/sglang_qwen2.5_*`.

```
python probes/probe_engine_logits.py --engine sglang --model Qwen/Qwen2.5-7B-Instruct-GPTQ-Int4 --repeats 6
python probes/probe_engine_logits.py --engine sglang --model Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int4 --repeats 6
python probes/probe_engine_logits.py --engine sglang --model Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int4 --repeats 6 --extra-arg enable-deterministic-inference=true
```

| Configuration | Meets n < 2048, k >= 2048? | Result over 12 comparisons |
|---|---|---|
| Qwen/Qwen2.5-7B-Instruct-GPTQ-Int4, TP=1 | no projection | bitwise identical in 12/12; same hash in both processes |
| Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int4, TP=1 | down_proj, n=1536, k=8960 | differs in 12/12; 30 or 60 of the 512 sampled tokens change in every comparison; first-run hashes differ between the two processes |
| Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int4, TP=1, `--enable-deterministic-inference` | down_proj, n=1536, k=8960 | differs in 12/12 (top-5 values in all 12, sampled tokens in 8 of 12) |

Kernel-level control (vLLM 0.28.0 `ops.marlin_gemm`, the same Marlin kernel family, random 4-bit weights, group size 128, shapes (m, n, k) = (16, 512, 3584), (16, 1024, 8192), (64, 512, 8192) and (1, 512, 8192), fp16 and bf16, five comparisons plus a baseline in each of two processes, 12 evaluations per configuration): `use_atomic_add=False` with `use_fp32_reduce=True` is bitwise identical in every comparison for all eight shape and dtype combinations, with the same hash in both processes. `use_atomic_add=True` differs in every comparison, with and without `use_fp32_reduce=True` (the pair SGLang's `apply_gptq_marlin_linear` passes), and its hashes differ between processes.

Engine-level control in vLLM (same 1.5B model and GPU, vLLM 0.28.0, `max_num_seqs=1`, otherwise the same method): with `VLLM_MARLIN_USE_ATOMIC_ADD` unset the run is bitwise identical in 12/12 with the same hash in both processes. With `VLLM_MARLIN_USE_ATOMIC_ADD=1` it differs in 12/12, and 30 to 90 of the 512 sampled tokens change in 9 of the 12 comparisons.

## Limits of the evidence

The source guard is demonstrably dead. The direct operator experiment uses vLLM's build of the Marlin kernel and random inputs; it is not a same-engine SGLang ablation. The SGLang end-to-end differences may include scheduling effects: in vLLM with atomic add off, the batched run (default `max_num_seqs`) still differed in 2 of 12 comparisons in top-5 values only, which is why the vLLM control above pins `max_num_seqs=1`. A Qwen2.5-7B TP=2 run also differed in 3 of 12 comparisons (top-5 values only, no token changes); since no 7B projection meets the shape condition at TP=2 (the `o_proj` shard is k=1792, n=3584), that result is not attributed to this guard. To isolate the contribution, SGLang would need to be repeated with the same build, weights, prompts and forced schedule, changing only the atomic guard and recording actual dispatch. That control has not been run. The numbers above are evidence on the named stack, not proof for every shape or build.

## Expected behaviour

Atomic-add reduction off unless explicitly enabled, matching the comment in the code and vLLM's behaviour, and forced off when `--enable-deterministic-inference` is set.

## Suggested fix

Replace the `if True: return` stub and the `if not True:` guard with a real switch: register `SGLANG_MARLIN_USE_ATOMIC_ADD = EnvBool(False)` in `python/sglang/srt/environ.py` and read it through `envs`, return False from `should_use_atomic_add_reduce` when `SGLANG_ENABLE_DETERMINISTIC_INFERENCE` is set (the serving hook sets it from `--enable-deterministic-inference`), and update the stale vLLM references in the comments and log message.
