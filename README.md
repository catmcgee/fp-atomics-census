# fp-atomics-census

A source census of floating-point atomic operations in LLM inference engines, with runtime observations on selected GPU stacks. It identifies potential obstacles to bit-exact replay; it does not certify a deployment or establish a complete verification protocol.

Eight repositories are pinned to 6 July 2026 commits in [scan-manifest.json](scan-manifest.json): vLLM, SGLang, FlashInfer, FlashAttention, Marlin, DeepGEMM, DeepEP and selected CUTLASS reduction paths. The [inventory](inventory/) contains source classifications and supporting references. Scanner matches and unresolved triage are recorded separately. The GPU measurements were made on 6–7 September 2026 against installed wheels, whose versions differ from the source census.

## What this adds

[Cankaya (2026)](https://arxiv.org/html/2606.00279v1) already distinguishes genuine run-to-run nondeterminism from changes caused by batch size, and lists per-pass batch information for replay (§§3.2 and 6). [Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) also treats batch invariance explicitly. This repository extends the source inventory and tests selected configurations. It does not present batch dependence as a new discovery or refute those works with experiments outside their stated scope.

The source reading identifies order-dependent accumulation in some adapter, quantisation, MoE, sampling and model-specific paths. Other paths use serialisation, one writer per destination, exact integer operations or opaque libraries. No order-dependent atomic was identified in the reviewed ordinary dense vLLM forward source paths under the stated configurations. That is a bounded source observation: generated kernels, library internals, unresolved candidates and other sources of nondeterminism prevent a universal conclusion. Throughput costs and protocol soundness were not measured here.

Unresolved candidates may be duplicate matches, helper definitions or additional sites. Their number is not a count of missed floating-point atomics. The ledger makes the unfinished triage explicit; source coverage is not claimed to be exhaustive.

Classes are **A** (potentially order-dependent floating-point accumulation), **A1** (one writer per destination), **A2** (serialised order), **A3** (gated path), **B** (exact or order-independent operation under the row's assumptions), **B-indirect** (an integer atomic can determine an order consumed by floating-point code), and **C** (opaque library or binary). Read `path`, `default_path_condition`, `gate`, `confidence` and `evidence` together. A default path is reachable on the named profile, not on every deployment. A source classification is not a measured runtime verdict.

`make validate` checks the schema, pinned checkout HEADs, exact ordered snippet bytes, reference ranges and candidate SHA/file/location associations. It reads source blobs from the pinned Git objects, so local checkout edits cannot silently alter the evidence. Missing source or candidate files fail validation. `--schema-only` is an explicit weaker check. External PyTorch gates are labelled as runtime dependencies because their implementation is outside the pinned sources.

## Configuration exclusions and unresolved controls

These are precautions for the reviewed paths, not sufficient conditions for bit-exact inference. A null result in a few repeats does not remove a source risk.

| Engine or path | Configuration to exclude or control | Source or evidence |
|---|---|---|
| vLLM LoRA | Disable LoRA, or test `VLLM_BATCH_INVARIANT=1` on the exact model | vllm-0018, vllm-0019 |
| vLLM quantised MoE | Exclude the `moe_wna16` CUDA path | vllm-0014 |
| vLLM Marlin | Keep `VLLM_MARLIN_USE_ATOMIC_ADD` unset | vllm-0010 |
| vLLM model-specific paths | Exclude mean pooling, Moondream3 and DiffusionGemma until their operator paths are controlled | vllm-0045, vllm-0046, vllm-0050 |
| vLLM ROCm gfx1100 | Exclude the reviewed packed GPTQ add loops pending a separate ROCm evaluation | vllm-0032–0037 |
| SGLang Marlin | Avoid fused, sharded projections with `n < 2048, k >= 2048`, or disable and verify the atomic branch in the same engine | sglang-0008; deterministic-inference mode alone did not remove the recorded differences |
| SGLang FP8 blockwise | Check actual dispatch before assuming the SM90 stream-K path is reached; avoid its nondeterministic branch | sglang-0011; the tested release wheels did not reach this source path |
| SGLang LoRA | Keep experimental virtual-expert and LoRA optimisation paths off | sglang-0019, sglang-0021 |
| SGLang Gemma3n audio | Control the CUDA floating-point cumsum path | sglang-0035 |
| FlashInfer CUTLASS fused MoE, including callers in engines | Use and verify the unfused finalisation path | flashinfer-0001 |
| FlashInfer SM120 fused MoE | Avoid the measured API/configurations for bit-exact use until backend and cause are isolated | API outputs differed at all tested token counts and top-k values; exact source kernel unknown |
| FlashInfer SM120 dense split-K GEMM | Treat its atomic epilogue as a separate source risk requiring its own direct probe | flashinfer-0011; the fused MoE experiment did not test it |
| FlashInfer sampling | Use deterministic top-p renormalisation; avoid uncontrolled multi-CTA top-k renormalisation and output-order dependence | flashinfer-0015–0018 |
| FlashAttention | Distinguish forward from backward; use and verify deterministic backward when training | backward rows are not inference evidence |
| DeepGEMM | Avoid the cross-batch `bmk,bnk->mn` einsum reduction | DeepGEMM-0001, DeepGEMM-0002 |
| CUTLASS callers | Do not select `ReductionMode::Nondeterministic` when order matters | Source defaults do not attest every caller or compiled specialisation |
| All engines | Pin runtime libraries, model/tokenizer revisions, parallel topology and actual dispatch; control batching or use tested batch-invariant kernels | Class C and generated kernels remain outside source-only guarantees |

A same-engine SGLang atomic-on/off intervention with the same model, schedule and weights remains necessary to isolate that end-to-end cause. The direct Marlin operator probes and the vLLM controls are supporting evidence, not that missing intervention.

`runtime_evidence.relation` distinguishes `operator_example`, `end_to_end_configuration`, `control`, `not_reached` and, when independently established, `exact_kernel`. No legacy result has verified identity tying the executed binary to a pinned inventory kernel. Report paths are preserved, duplicate tags are not discarded, and stale attachments are removed on regeneration. An invalid, rejected or missing measurement cannot become `DIFFERS` or `identical`.

Several qualifications matter when interpreting the legacy records:

- PyTorch's `det` arms used `warn_only=True`. They are not strict deterministic enforcement. New `det_strict` arms reject unsupported operations and record the rejection.
- Generic `index_add_`, scatter and cumsum examples do not establish that an engine reached the cited call site. The bf16/fp16 GEMM sweep does not test FP8 `scaled_mm`. FlashInfer top-k does not test the distinct vLLM/SGLang implementations.
- cuBLASLt algorithm logs came from a separate diagnostic child process. They are not executed-kernel identities for the measured repeats. A stable output also does not establish that atomics were absent.
- The SM120 fused MoE outputs differed with 16, 512 and 4096 tokens and top-k 2, 4 and 8. Those reports did not store ULP distributions or selected backends. Their correlation with an unquantised reference does not establish quantised-kernel correctness or identify the cause. Importing helpers from a dense split-K module does not execute its epilogue. The revised probe adds top-k 1 and ULP/finite diagnostics; those new arms have not been run on a GPU here.
- Two fixed, finite, already-rounded contributions added to zero commute; this narrow observation about finalisation does not prove the upstream GEMM deterministic. Two-rank all-reduce is similarly a weak smoke test for associativity. The new cancellation case requires at least three ranks.
- FlashInfer plain all-reduce fusion **was run** on two H100s and returned matching hashes. NVLS and cuDNN are not established by those records. SGLang's default B200 bf16 arm has differences; the separately forced `trtllm_mha` arm has a null result. These are separate configurations.

## Batch-shape experiments

[The hypothesis](docs/SHAPE_HYPOTHESIS.md) is a research question, not an established invariant. [The runbook](probes/shape/RUNBOOK.md) describes the instruments and their limits. `make shape-tables` reanalyses raw observations before printing the tables; `make check-derived` rejects stale summaries, CSV and generated README blocks.

The legacy E2 logs contain 2,001 forward passes and 115 empty scheduler calls. Empty calls retained stale batch rows in the old hook and are now excluded. At repeated recorded histories, no hidden/output-hash violation was observed. E2 also reports singleton history groups, which provide no repeatability test. The shape key now preserves batch order, target placement, parallel settings and recorded dispatch; it still does not capture every kernel planner decision.

E3 reproduced two scripted trajectories in fresh processes (37 and 42 forward passes). **P2, reconstruction from a recorded schedule and a rebuilt midstream state, was not tested.** The script injects requests after a fixed number of scheduler steps; it does not drive the second run from the first run's trace or teacher-force the recorded tokens.

E4 compares a target against random-token neighbours of matching lengths. All saved targets now have 32 non-null forward observations. The legacy target is slot 0, with prefix caching off, synchronous arrivals and one of four short prompts repeated across the batch. A prompt-construction bug excluded the intended longer prompts; new runs use an explicitly versioned mixed-length set. These results do not establish content independence for arbitrary targets, mixed prefill, cache reuse or shared-prefix planners.

The old flags did not implement a compilation/graph factorial: `--cudagraph 0` set `enforce_eager=True`, disabling both; `--no-compile --cudagraph 1` also resolved to no graphs in those runs. The recorded contrast is default execution versus eager execution. In default execution, the MoE target differed and the forced per-tensor FP8 target did not; in eager execution the opposite was observed. Routing counts and FP8 scales changed in the eager arms, but that correlation does not isolate why default and eager execution differ. The new harness independently requests compile and graph settings, records resolved settings and rejects mismatches. A four-arm GPU validation remains unrun.

E5 compares H100 and RTX PRO 6000 free-running trajectories: hidden hashes differ in every compared step. GPU and driver differ, and subsequent tokens diverge. This is a two-stack observation, not an isolated GPU effect or a teacher-forced comparison.

Legacy hidden hashes are truncated SHA-256 values; output hashes flatten sparse top-5 values without vocabulary labels. Those raw measurements cannot be upgraded retrospectively. New observations hash full SHA-256 with dtype/shape information and preserve vocabulary IDs, position boundaries and API float bits; the hook also hashes full logit rows. Neither version commits the full KV cache. Missing hashes, joins, requests, tails or mismatched shapes fail the relevant comparison instead of being accepted on a common prefix.

## Verification implications

A recorded batch history can help reproduce an execution, but a history chosen by the operator can still carry operator-chosen information. Logging or committing that choice does not remove the choice. [Findings notes](docs/FINDINGS.md) distinguish replay soundness from scheduler freedom and give the correct conditional bound on distinguishable trajectories. No covert-channel capacity or complete security guarantee was measured here; comparison with tolerance-based verification such as [DiFR](https://arxiv.org/html/2511.20621v1) needs a specified threat model.

## Reproduce and extend

```sh
make venv                    # frozen CPU scanner/analyser and regression-test dependencies
make clone                   # eight pinned source checkouts
make test
make validate
make summary
make shape-tables
make docs                    # regenerate summaries, runtime attachments, CSV and README blocks
make check-derived           # read-only consistency check
make census REPO=vllm         # scanner only; does not regenerate human triage
```

`uv.lock` pins the CPU tooling, including a CPU-test PyTorch version. It is not a lock for the historic CUDA stacks. [probes/stacks.json](probes/stacks.json) records the available legacy package versions and their gaps. GPU requirements are exploratory; use separate environments, supply explicit model revisions and archive the complete installed environment for each new campaign. The revised GPU instrumentation has CPU regression coverage but has not been exercised against vLLM/CUDA in this change.

New reports use immutable run directories and exclusive writes. They record a run ID, time, source digest, installed distributions, deterministic flags, available runtime versions, configuration and available model revision information. Missing weight, tokenizer, cubin, topology or selected-kernel hashes are explicitly unknown; a package version alone does not provide them. This prevents new reports from claiming provenance that has not been captured. Legacy raw reports remain unchanged.
